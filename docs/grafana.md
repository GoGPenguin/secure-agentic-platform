# Grafana infrastructure (W05-B.3.2)

## Ownership and deployment boundary

`platform-root` owns the `grafana` Application in `argocd`. That Application
uses the existing `secure-monitoring` AppProject and renders `monitoring/grafana`
with Kustomize. It owns exactly one Deployment, ClusterIP Service,
ServiceAccount and two ConfigMaps in `monitoring`. Existing Applications,
AppProjects and RBAC are unchanged. The root already owns the namespace.

The required `monitoring/grafana-admin` Secret is owned by an authorized
operator, outside both Applications. It is never generated by Kustomize or
stored in Git. Create it before enabling this change in the root's tracked
branch: automatic sync can start the child Application immediately. Argo CD
sync waves cannot establish readiness of an externally managed Secret.
Missing Secret keys prevent the Pod from starting; the Secret is not optional.
Nonempty, strong values are an operator precondition.

There are no dashboard JSON files or dashboard providers in this increment.
The later HTTP 5xx panel must calculate **percentage of completed requests**,
not errors per second: `100 * sum(rate(http_requests_total{job="platform-api",status_code=~"5.."}[$__rate_interval])) / sum(rate(http_requests_total{job="platform-api"}[$__rate_interval]))`.
Handle absent 5xx series separately from missing targets; show no traffic as
undefined rather than claiming a meaningful error percentage for a zero denominator.

## Create the admin Secret before deployment

Run this procedure only as an operator already authorized to create Secrets
in `monitoring`, against the intended kube-context. It does not require
granting permissions to Grafana. The namespace must already exist.
Generate and retain a strong password in a password manager first.

Example for an interactive Bash session on Linux, outside session recording
and without shell tracing. This uses temporary files in RAM, does not put the
password in command arguments, and does not print Secret YAML:

```bash
(
  set +x
  set -euo pipefail
  umask 077
  credential_dir=$(mktemp -d /dev/shm/grafana-admin.XXXXXX)
  trap 'unset grafana_password; rm -rf -- "$credential_dir"' EXIT
  printf '%s' 'admin' > "$credential_dir/admin-user"
  IFS= read -r -s -p 'Password from password manager: ' grafana_password
  printf '\n'
  test -n "$grafana_password"
  printf '%s' "$grafana_password" > "$credential_dir/admin-password"
  unset grafana_password
  kubectl -n monitoring create secret generic grafana-admin \
    --from-file=admin-user="$credential_dir/admin-user" \
    --from-file=admin-password="$credential_dir/admin-password"
)
```

If the Secret already exists, stop and follow the rotation procedure; do not
delete it just to rerun creation. Keep credentials out of terminal logs,
screenshots and exported manifests. Kubernetes Secret encoding is not
encryption: cluster access controls and encryption at rest remain platform
responsibilities. Do not add Argo CD ownership/tracking metadata to this Secret.

The Secret is mounted read-only with mode `0440`; `fsGroup: 472` grants the
non-root process access. The official entrypoint reads `admin-user` and
`admin-password` through `GF_SECURITY_ADMIN_USER__FILE` and
`GF_SECURITY_ADMIN_PASSWORD__FILE`. It converts them into process environment
settings internally; this is not protection against a privileged process
inspector. No credential values appear in the Deployment or ConfigMaps.

## Image and container security

The image is `grafana/grafana:13.2.3`, additionally pinned to registry digest
`sha256:b28bae15e219c998fb0e0424ed724930cc61b1f61fb404d47c862f9a23f9e572`.
Verification during implementation pulled the official image, observed that
digest, ran `grafana --version` (13.2.3), and inspected `/run.sh` for `__FILE`
support. Its default user is UID 472 with GID 0; this Deployment explicitly
uses UID **and GID 472**, verified in the isolated smoke test. Registry digest
verification is not image-signature verification or a vulnerability scan.
Review Grafana security advisories before each promotion and upgrade the
version and digest together through Git review.

The container drops all capabilities, prohibits privilege escalation, uses
RuntimeDefault seccomp and has a read-only root filesystem. Neither the
ServiceAccount nor the Pod automounts a Kubernetes token. Grafana reads
projected files and reaches Prometheus over HTTP; it needs no Role,
ClusterRole, API discovery sidecar or Kubernetes API client credentials.

The Service is ClusterIP on port 3000. There is no Ingress, NodePort,
LoadBalancer, host networking or host port. Anonymous access and user/org
self-registration are disabled. ClusterIP is reachable within the cluster;
it does not provide network isolation. This increment adds no NetworkPolicy,
which the unchanged AppProject does not allow.

## Writable paths, storage and resources

`/var/lib/grafana` is a writable `emptyDir` limited to 1Gi. It holds SQLite,
session/application state, plugin directories and any generated local data.
The official entrypoint creates the plugin directory; automatic plugin
preinstallation is disabled. Logs go to stdout/stderr. `/tmp` is a separate
writable `emptyDir` limited to 128Mi for temporary files. All configuration
and credential mounts are read-only. `fsGroup: 472` makes the Kubernetes
volumes writable/readable as appropriate without a root init container.
The image directory's ownership alone would not grant access to a mounted
volume, because the mount hides the image directory.

Requests are 100m CPU, 256Mi memory and 256Mi ephemeral storage; limits are
500m CPU, 512Mi memory and 2Gi ephemeral storage. The storage limit leaves
headroom for logs beyond the bounded data/tmp volumes. These are initial
lab values; observe usage before tuning. Disk-backed emptyDir consumption
counts toward ephemeral storage, and resource pressure can evict the Pod.

One replica and `Recreate` avoid overlapping independent SQLite-backed
instances. A container restart within a Pod preserves emptyDir; Pod
replacement, rescheduling or a Deployment rollout loses the database.
Expect downtime during replacement. The data source is reprovisioned, and
the admin account is recreated from the current Secret. Local users, password
changes, sessions and UI-created content are lost. Persistent storage and
backups require a separate design: PVCs are outside the current AppProject
allowlist.

Startup, readiness and liveness probes use `/api/health`. Startup allows up
to approximately five minutes; readiness checks every five seconds and
liveness tolerates six failures ten seconds apart. This endpoint checks
Grafana/database health, not Prometheus availability. An unavailable Prometheus
must not cause Grafana restart loops.

## Configuration propagation and validation

Kustomize generates `grafana-config` from `config/grafana.ini` and
`grafana-datasources` from `config/datasources.yaml`. Stable names avoid
orphan ConfigMaps under `prune=false`. They sync in wave -1 before the
Deployment. Both are directory mounts without `subPath`.

Argo CD updates the ConfigMaps; Kubernetes eventually updates mounted files.
Grafana loads these settings/data sources on startup, so file projection
alone does not establish that the running process has applied them.
`checksum/config` in the Pod template triggers replacement when configuration
changes. Run:

```bash
kubectl kustomize monitoring/grafana
python3 scripts/validate-grafana-config.py
git diff --check
```

The validator requires kubectl with Kustomize support and PyYAML 6.0.3. It
renders locally without contacting the cluster, checks every output resource
against the existing AppProject's namespace resource allowlist, and validates
the checksum. The checksum is SHA-256 over UTF-8 bytes of Python
`json.dumps(config_data, sort_keys=True, separators=(",", ":"))`, where
`config_data` maps generated ConfigMap names to their decoded `data` mappings.
On failure it prints the expected checksum; update the Deployment annotation
with the configuration in the same PR. It never edits files. This check is
manual in this increment; it has not been added to CI or branch protection.

The data source has UID `prometheus`, server-side proxy access, the URL
`http://prometheus.monitoring.svc.cluster.local:9090`, a 30s interval matching
the existing scrape interval, and `editable: false` to prevent UI changes
from becoming authoritative. No Prometheus credentials are needed here.
Since automated pruning is disabled, removing a managed resource from Git
requires deliberate cleanup. Future dashboard JSON should be mounted from
Git and polled with `allowUiUpdates: false`; none is provisioned yet.

## Credential rotation and recovery

Grafana's admin user/password settings bootstrap a fresh database. Updating
the Secret or restarting the container does **not** change a password in an
existing database. Mounted Secret refresh does not make Grafana reread it.

For normal rotation, retain the new password in the password manager, change
the current admin password through Grafana's authenticated account flow, then
update only `admin-password` in the external Secret through protected operator
tooling. Verify a fresh login with the new password and rejection of the old
one. Coordinate this short two-system operation to avoid Pod replacement
between changes. If one step fails, reconcile the live account and Secret
before considering rotation complete. Avoid changing the bootstrap username
as part of password rotation; that does not rename an existing account.

For lost access while SQLite still exists, an already authorized operator can
use the pinned image's CLI against the actual database and configuration:

```text
grafana cli --homepath /usr/share/grafana \
  --config /etc/grafana/config/grafana.ini \
  admin reset-admin-password --password-from-stdin
```

The image's CLI help was checked for `--password-from-stdin`. Supply the new
password over protected stdin rather than as an argument, do not allocate a
terminal that echoes it, and synchronize the external Secret and password
manager afterward. Remote execution requires existing operator access to
`pods/exec`; no such permissions are granted to Grafana. Confirm the target
admin ID if it differs from the CLI default of 1.

If the Pod/database is already lost, recover using the credential currently
stored in the Secret; all other local account state is gone. Deliberately
replacing a Pod can reset the lab database but destroys all local state and
is not the normal password rotation procedure. There is no automatic password
reset init container and no guarantee of recovering unprovisioned state.

## Implementation verification and later runtime checks

Local validation rendered five allowed monitoring resources and verified the
checksum. Kubeconform v0.7.0 in strict mode against Kubernetes 1.35.0 schemas
reported five valid resources, zero invalid, zero errors and zero skipped:

```bash
kubectl kustomize monitoring/grafana | docker run --rm -i \
  ghcr.io/yannh/kubeconform:v0.7.0 -strict -summary -kubernetes-version 1.35.0
```

This validates the child resources, not the Argo CD Application CRD. An
isolated Docker smoke test ran the pinned image as 472:472 with
all capabilities dropped, no privilege escalation, a read-only root filesystem,
writable data/tmp mounts and disposable file credentials. `/api/health`
reported database `ok` and version 13.2.3; authenticated retrieval of data
source UID `prometheus` confirmed the URL, default status and `readOnly: true`.
This does not validate in-cluster DNS, projected-volume ownership, admission,
or actual connectivity to the existing Prometheus. No Kubernetes deployment
was performed during implementation.

After an independently authorized deployment, check root and child health
separately, Pod rollout, UID/GID and volume access, absence of the service
account token, and the data-source health check against the real Prometheus.
Use `kubectl -n monitoring port-forward --address 127.0.0.1 svc/grafana 3000:3000`
for local access. Do not infer successful Prometheus queries from Argo sync
status or Grafana's own health endpoint.
